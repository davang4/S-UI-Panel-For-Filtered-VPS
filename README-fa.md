# S-UI-Panel-For-Filtered-VPS — راهنمای فارسی

**وی‌پی‌ان شخصی برای سروری که IP آن فیلتر شده.**

اگر IP سرور روی بعضی (یا همه) اپراتورها فیلتر است، وصل کردن هر پروتکل VPN
مستقیم به آن IP جواب نمی‌دهد — فیلتر در سطح IP است، پس خود IP باید پشت
کلادفلر پنهان شود. این نصب دقیقاً همین کار را می‌کند؛ بدون سرور ایران،
بدون دامنه شخصی و بدون باز کردن هیچ پورتی:

- **پنل s-ui** روی سرور برای ساخت کاربر با سقف حجم و تاریخ انقضا (فقط
  localhost، هرگز مستقیم در معرض اینترنت نیست).
- **دو تونل موقت کلادفلر** (`trycloudflare.com`): یکی جلوی ورودی VLESS،
  یکی جلوی پنل. آدرس تونل‌ها با هر ری‌استارت عوض می‌شود — هیچ بخشی از
  سیستم به ثابت ماندن آن‌ها وابسته نیست.
- **یک ورکر کلادفلر** (`workers.dev`) به‌عنوان تنها آدرس ثابتی که کلاینت‌ها
  لازم دارند: سابکریپشن هر کاربر را می‌دهد و همیشه به آدرس *فعلی* تونل
  اشاره می‌کند، و پنل را هم با یک آدرس ثابت در دسترس می‌گذارد. یک تایمر
  روی سرور هر ۶۰ ثانیه ورکر را به‌روز نگه می‌دارد.
- **جداسازی ترافیک ایران** (اختیاری، قابل ویرایش): دامنه‌ها و IPهای ایرانی
  مستقیم می‌روند، بقیه از VPN. تنظیمات routing خود پنل هم خودکار به
  پروفایل کلاینت اضافه می‌شود.

کلاینت‌ها: **Hiddify / v2rayNG** (لینک سابکریپشن base64) و **اپ رسمی
sing-box** (پروفایل JSON کامل؛ ورکر با دیدن user-agent آن، خودش JSON
می‌دهد). پروتکل: **VLESS + WebSocket + TLS** — وایرگارد، OpenVPN و
شدوساکس ساده جلوی DPI دوام نمی‌آورند، و XHTTP هم از تونل کلادفلر رد
نمی‌شود (تست شده).

> تست‌شده روی Ubuntu 22.04 (سرور RackNerd آمریکا) با s-ui 1.6.8،
> cloudflared 2026.11.2 و کلاینت sing-box 1.14 (اندروید/iOS).

## نصب با یک دستور

روی یک سرور تازه Ubuntu/Debian، با کاربر root (یا `sudo`):

```bash
curl -fsSL https://github.com/davang4/S-UI-Panel-For-Filtered-VPS/archive/refs/heads/main.tar.gz \
  | tar xz && cd S-UI-Panel-For-Filtered-VPS-main && sudo bash install.sh install
```

یا اگر دوست داری اول اسکریپت‌ها را بخوانی (توصیه می‌شود — ببین
[SECURITY.md](docs/SECURITY.md)):

```bash
git clone https://github.com/davang4/S-UI-Panel-For-Filtered-VPS.git
cd S-UI-Panel-For-Filtered-VPS
sudo bash install.sh install
```

نصب‌کننده یک بار توکن API کلادفلر را می‌پرسد (مخفی تایپ می‌شود و در
`~/sui-vpn/state.env` با دسترسی 600 ذخیره می‌شود، هرگز چاپ نمی‌شود).
توکن را با این لینک یک‌کلیکه بساز — دسترسی‌ها از قبل تیک خورده‌اند،
فقط «Continue to summary» و بعد «Create Token» را بزن:

[ساخت توکن API کلادفلر](https://dash.cloudflare.com/profile/api-tokens?permissionGroupKeys=%5B%7B%22key%22%3A%22workers_scripts%22%2C%22type%22%3A%22edit%22%7D%2C%7B%22key%22%3A%22workers_kv_storage%22%2C%22type%22%3A%22edit%22%7D%2C%7B%22key%22%3A%22account_settings%22%2C%22type%22%3A%22read%22%7D%5D&accountId=*&zoneId=all&name=SUI-Panel-Sub)

یا دستی از اینجا: dash.cloudflare.com → My Profile → API Tokens →
Create Token، با این دسترسی‌ها:

- Account → **Workers Scripts → Edit**
- Account → **Workers KV Storage → Edit**
- Account → **Account Settings → Read**

دسترسی Zone لازم نیست. توکنی با همین دو دسترسی نمی‌تواند به دامنه‌ها،
DNS یا تونل‌هایت دست بزند.

ساخت همین توکن **تنها قدم دستی سمت کلادفلر** است. بقیه کارها خودکار
انجام می‌شود: نصب‌کننده توکن را چک می‌کند، اکانت را خودش پیدا می‌کند
(فقط اگر توکن چند اکانت ببیند می‌پرسد)، اگر اکانت ساب‌دامین
`workers.dev` نداشته باشد خودش یکی می‌سازد، KV namespace را می‌سازد یا
استفاده می‌کند، ورکر را آپلود می‌کند و مسیر `workers.dev` آن را فعال
می‌کند. تنها چیزی که هیچ اسکریپتی نمی‌تواند برایت انجام بدهد ساخت همان
توکن اول است — کلادفلر برای ساخت اولین credential به انسان نیاز دارد.

چیز دیگری نمی‌پرسد: نام کاربری، رمزها، مسیر مخفی پنل، مسیر WS و رمز
سابکریپشن همه روی سرور ساخته می‌شوند. **بلوک آخر نصب را ذخیره کن** —
رمز پنل و لینک سابکریپشن فقط یک بار نشان داده می‌شوند.

**پورت‌ها.** نصب‌کننده سه پورت لوکال می‌خواهد: پنل `2095`، سرور
سابکریپشن `2096`، اینباند `10087`. اگر یکی از آن‌ها را برنامه دیگری
گرفته باشد، نصب‌کننده می‌گوید و می‌گذارد پورت دیگری بدهی — اینتر را
بزن تا همان پورت خالی رندمی که پیشنهاد می‌دهد را بگیرد. وقتی ورودی
ترمینال نیست (مثلاً نصب را در یک tmux جدا شده paste کرده‌ای)، خودش یک
پورت خالی رندم انتخاب می‌کند و می‌گوید کدام را گرفت. پورتی که خود s-ui
ما گرفته باشد را بی‌صدا نگه می‌دارد، پس اجرای دوباره نصب‌کننده هیچ‌وقت
پنل را جابه‌جا نمی‌کند. برای انتخاب پورت‌ها از اول:

```bash
PANEL_PORT=12095 SUB_PORT=12096 IN_PORT=11087 sudo -E bash install.sh install
```

پورت‌های نهایی در `~/sui-vpn/state.env` ذخیره می‌شوند، پس اجراهای بعدی
و `sui_setup.py` همان‌ها را استفاده می‌کنند.

## چه چیزی نصب می‌شود — و چه چیزی دست نمی‌خورد؟

| نصب می‌شود | دست نمی‌خورد |
|---|---|
| `~/sui-vpn` (باینری‌ها، دیتابیس، state، لاگ‌ها) | بقیه چیزهای روی سرور |
| سرویس‌های systemd: `sui-panel`، `sui-tunnel`، `sui-panel-tunnel`، `sui-sync(.timer)` | فایروال عوض نمی‌شود، هیچ پورت عمومی باز نمی‌شود |
| کلادفلر: یک ورکر (`sui-sub`)، یک KV namespace (`sui-sub`)، یک API توکن | دامنه‌ها، DNS و تونل‌های موجود |
| پنل s-ui روی `127.0.0.1:2095`، ورودی روی `127.0.0.1:10087` | — |

پورت‌ها قابل تغییرند: `PANEL_PORT=12095 SUB_PORT=12096 IN_PORT=11087 sudo bash install.sh install`
نام اولین کاربر پیش‌فرض `main` است؛ با `FIRST_CLIENT_NAME=alice` عوضش کن.
برای رد کردن توکن بدون پرامپت تعاملی (مثلاً داخل tmux که `read` مخفی
ممکن است خطا بدهد)، قبل از نصب `CF_API_TOKEN` و `CF_ACCOUNT_ID` را
export کن.

## مدیریت

بعد از نصب، همه دستورها از هر پوشه‌ای هم کار می‌کنند — بدون `cd`.
`sudo filtersui` بدون دستور یک منوی شماره‌دار باز می‌کند (بنر، آدرس
ثابت پنل و کد سرور بالای منو نوشته می‌شوند، تا بدانی روی کدام
سروری)؛ یک عدد بزن — نیازی به نوشتن اسم دستور نیست — و بعد از هر کار
منو دوباره برمی‌گردد تا ۰ را بزنی. عدد به‌عنوان دستور مستقیم هم کار
می‌کند (`sudo filtersui 3` یعنی `status`)، و دستورهای مستقیم هم سر
جاشان هستند. منو انگلیسی است و خودِ filtersui نسخه دارد
(`FILTERSUI_VERSION`، الان ۱.۰.۰) — `sudo filtersui version` نسخه آن
را با نسخه‌های s-ui و cloudflared با هم نشان می‌دهد:

```bash
sudo filtersui          # منوی شماره‌دار
sudo filtersui status   # یا: sudo sui-vpn status
sudo sui-vpn show
```

`sudo bash install.sh help` (در پوشه نصب) همین لیست را چاپ می‌کند.
اجرای بدون دستور قبلاً نصب کامل را شروع می‌کرد — حالا منو را باز
می‌کند؛ برای نصب صریح `install` را بزن (نصب با یک دستور بالا همین کار
را می‌کند).

کارهای مخرب همیشه اول تایید می‌گیرند، چه در منو چه در خط دستور:
`uninstall` (پنل، تونل‌ها و `~/sui-vpn` را حذف می‌کند)،
`change-subdomain` (آدرس ثابت همه ورکرهای اکانت را عوض می‌کند)، و
`restore` (`~/sui-vpn` را با بکاپ جایگزین می‌کند). `update-sui` و
اجرای دوباره `install` تایید نمی‌گیرند — قبلشان از دیتابیس و state
بکاپ گرفته می‌شود (`~/sui-vpn/backups/`، ۵ تای آخر نگه داشته
می‌شوند)، پس قابل برگشت‌اند.

### مرجع دستورها

| دستور | چه کار می‌کند |
|---|---|
| `menu` | منوی شماره‌دار (پیش‌فرض وقتی دستوری نداده باشی). |
| `install` | نصب کامل (پنل + تونل‌ها + ورکر + تایمر سینک). اجرای دوباره‌اش امن است: state موجود را نگه می‌دارد و فقط چیزهای جاافتاده را کامل می‌کند، و قبلش از دیتابیس و state بکاپ می‌گیرد. |
| `show` | آدرس پنل، آدرس فعلی تونل، لینک ثابت سابکریپشن، ورود پنل. |
| `status` | وضعیت سرویس‌ها، آدرس تونل‌ها، خط‌های آخر لاگ تونل، آخرین سینک، و چک سلامت واقعی: `/health` و `/sub` ورکر، پنل از طریق تونل، وضعیت آخرین سینک. وقتی چیزی خراب است از اینجا شروع کن. |
| `sync-now` | سینک دستی کلاینت‌ها با ورکر (تایمر هر ۶۰ ثانیه خودش این کار را می‌کند، و وقتی آدرس تونل عوض شود فوراً). |
| `sync-now --dry-run` | پیش‌نمایش چیزی که سینک می‌شود، با لینک‌های کامل. چیزی نمی‌نویسد. |
| `sync-now --force` | بازنویسی همه‌چیز در KV حتی اگر چیزی عوض نشده باشد (بعد از جابه‌جایی ورکر/KV، یا وقتی سرور دیگری `panel:host` این سرور را بازنویسی کرده). |
| `deploy-worker` | آپلود دوباره `worker.js` به کلادفلر بعد از ویرایش آن. ورکر + KV همین سرور را دوباره استفاده می‌کند (با کد سرور)؛ اگر اسم‌ها در `state.env` گم شده باشند، ورکر + KV موجود همین سرور را پیدا و برمی‌دارد، به‌جای اینکه جدید بسازد. |
| `change-subdomain [name]` | عوض کردن ساب‌دامین workers.dev اکانت با یک اسم دلخواه (آدرس ثابت همه ورکرهای آن اکانت عوض می‌شود؛ بعدش روی هر سرور دیگر `deploy-worker` را دوباره بزن). |
| `update-sui` | جایگزینی s-ui با جدیدترین نسخه گیت‌هاب. اول نسخه را چک می‌کند — اگر s-ui همین حالا هم آخرین نسخه باشد، می‌گوید «آخرین نسخه است» و هیچ کاری نمی‌کند (نه دانلود، نه ری‌استارت). پرش نسخه اصلی (۱ به ۲) اول می‌پرسد، چون نسخه اصلی جدید ممکن است موقع اولین اجرا دیتابیس پنل را ریست کند. اول چک می‌کند باینری جدید اجرا می‌شود و از نسخه قبلی بکاپ با تاریخ نگه می‌دارد — و قبل از دست زدن به باینری، از دیتابیس s-ui و state هم بکاپ می‌گیرد (`~/sui-vpn/backups/`، ۵ تای آخر نگه داشته می‌شوند). |
| `panel-on` / `panel-off` | باز کردن / بستن دسترسی اینترنتی پنل. خاموش یعنی پنل فقط از راه SSH forward در دسترس است. |
| `backup` | بکاپ `~/sui-vpn` (دسترسی ۶۰۰) در پوشه خانگی، با نوار پیشرفت (روی ترمینال)، حجم آن و دستور `scp` برای دانلودش. همه رمزها را دارد — از سرور خارجش کن. |
| `restore [file]` | برگرداندن `~/sui-vpn` از بکاپ و ری‌استارت سرویس‌ها. بدون فایل، بکاپ‌های روی همین سرور را لیست می‌کند (بکاپ‌های خودکار قبل از تغییر + بکاپ‌های دستی، از جدید به قدیم، با تاریخ و حجم) و آن که با عدد انتخاب می‌کنی را برمی‌گرداند؛ مسیر فایل هم برای بکاپی که از بیرون کپی شده هنوز کار می‌کند. روی سرور تازه، بعدش `install` را بزن (state برگردانده‌شده را نگه می‌دارد). |
| `version` | نشان دادن نسخه‌های روی این سرور: filtersui، s-ui، cloudflared. |
| `uninstall` | حذف نصب از سرور (پایین). اول تایید می‌گیرد. |
| `help` | نمایش لیست دستورها. |

### کاربران

پنل را باز کن (آدرس ثابت ورکر + مسیر مخفی، یا `install.sh show`)،
Clients → add. مقدار Volume (گیگابایت، `0` = نامحدود) و Expiry را بده.
تا حدود ۶۰ ثانیه بعد، سینک سابکریپشن او را به ورکر می‌نویسد؛ لینک
سابکریپشن او `https://<worker>.workers.dev/sub/<secret>/<name>` است —
نصب‌کننده Subscription URI پنل را خودش تنظیم کرده، پس لینک را مستقیم
از پنل کپی کن. حجم و انقضا را خود سینک اعمال می‌کند: کاربر منقضی یا
پرحجم، خودکار از ورکر حذف می‌شود.

- **غیرفعال / حذف کاربر:** Enable را خاموش کن یا کلاینت را در پنل حذف
  کن. در سینک بعدی (حداکثر ۶۰ ثانیه) کلیدهای او از ورکر حذف می‌شوند و
  سابکریپشن او از کار می‌افتد. برای باطل کردن فوری یک لینک لو رفته،
  کاربر را حذف کن و `sync-now` را بزن.
- **تغییر نام کاربر:** کلید اسم قبلی حذف و کلید جدید منتشر می‌شود.
  لینک جدید را از پنل بده.
- **به‌روزرسانی اپ کلاینت:** در Hiddify / v2rayNG / sing-box،
  سابکریپشن ریموت را Update کن. آدرس هیچ‌وقت عوض نمی‌شود، حتی وقتی
  تونل ری‌استارت می‌شود.

### لاگ‌ها و سلامت

```bash
sudo bash install.sh status                 # سرویس‌ها + لاگ تونل + آخرین سینک + چک سلامت
sudo journalctl -u sui-panel -n 50          # لاگ پنل
sudo journalctl -u sui-tunnel -n 50         # لاگ تونل
sudo journalctl -u sui-sync.service -n 20   # اجراهای اخیر سینک
curl -s https://<worker>.workers.dev/health   # ورکر زنده است؟ باید "ok" چاپ کند
sudo bash install.sh sync-now --dry-run     # ورکر الان چه چیزی سرو می‌کند
```

چک سلامت آخر `status` سرتاسری است، نه فقط «پروسه زنده است»: `/health`
ورکر را می‌گیرد، `/sub` همین کلاینت را از ورکر می‌گیرد (KV + ورکر +
کلید کلاینت در یک درخواست)، صفحه ورود پنل را **از طریق تونل خودش**
باز می‌کند، و آخرین سینک را گزارش می‌دهد (کی اجرا شد و اگر خطا داشت
چه خطایی). یک خط `FAIL` همان‌جا می‌گوید کدام حلقه خراب است، به‌جای
حدس زدن.

### بکاپ و برگرداندن

```bash
sudo bash install.sh backup                              # -> ~/sui-vpn-backup-<date>.tar.gz
sudo bash install.sh restore                              # بکاپ‌های روی سرور را لیست می‌کند، با عدد انتخاب کن
sudo bash install.sh restore ~/sui-vpn-backup-<date>.tar.gz
```

بکاپ شامل `state.env` (رمز پنل، توکن کلادفلر، UUID کاربرها، رمز
سابکریپشن) و دیتابیس s-ui است — همه چیزی که برای ساختن دوباره همان
نصب با همان لینک‌های سابکریپشن لازم است. **حتماً از سرور خارجش کن**؛
بکاپی که فقط روی سرور است با سرور می‌میرد. `backup` مسیر فایل، حجم
آن و دستور `scp` برای دانلودش را چاپ می‌کند (یا با SFTP، مثلاً در
Termius، دانلودش کن). `restore` بدون فایل، بکاپ‌های روی همین سرور را
لیست می‌کند — بکاپ‌های خودکار قبل از تغییر در `~/sui-vpn/backups/` و
بکاپ‌های دستی در پوشه خانگی، از جدید به قدیم با تاریخ و حجم — و آن که
با عدد انتخاب می‌کنی را برمی‌گرداند (قبلش هنوز تایید می‌گیرد، چون
`~/sui-vpn` را جایگزین می‌کند). `backup` و `restore` روی ترمینال نوار
پیشرفت نشان می‌دهند (چک‌پوینت‌های tar گنو، بدون وابستگی اضافه؛ وقتی
ترمینال نیست، همان `tar` ساده اجرا می‌شود). برای جابه‌جایی به سرور
جدید: بکاپ را منتقل کن، `install` را بزن (state برگردانده‌شده را نگه
می‌دارد) و بعد `restore` را اجرا کن — یا اول restore و بعد install؛
هر دو ترتیب جواب می‌دهد.

### حذف کامل

```bash
sudo bash install.sh uninstall
```

این کار چهار سرویس systemd را خاموش و حذف می‌کند و `~/sui-vpn` را از
سرور پاک می‌کند، و چیز دیگری را دست نمی‌زند. سمت کلادفلر می‌ماند — اگر
می‌خواهی کامل پاک شود، دستی حذفش کن:

۱. dash.cloudflare.com → Workers & Pages → `sui-sub` → Settings →
   Delete (این کار آدرس `workers.dev` را هم پاک می‌کند).
۲. Workers & Pages → KV → `sui-sub` → Delete.
۳. My Profile → API Tokens → `SUI-Panel-Sub` → Delete.

فقط باطل کردن توکن هم سینک را کامل متوقف می‌کند، پس قدم ۳ مهم‌ترین
قدم است.
می‌شود.

## چطور کار می‌کند؟

```
گوشی --TLS--> لبه کلادفلر (trycloudflare.com)
                   --WS--> cloudflared روی سرور --> 127.0.0.1:10087 (ورودی VLESS در s-ui)
گوشی --HTTPS--> ورکر (workers.dev)
                   --KV--> آدرس فعلی تونل + لینک هر کاربر
                   --HTTPS--> تونل پنل --> 127.0.0.1:2095 (پنل s-ui)
سرور --هر ۶۰ ثانیه--> sync.py دیتابیس s-ui و لاگ تونل را می‌خواند --> KV کلادفلر
```

تصویر کامل در [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)، مدل تهدید در
[docs/SECURITY.md](docs/SECURITY.md) و خطاهای معروفی که قبلاً خوردیم و
رفع شد در [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md).

## چند سرور

یک ورکر + یک KV دقیقاً برای **یک** سرور است — ولی یک اکانت کلادفلر و
یک توکن API برای هر تعداد پنل کافی است. نصب تازه همیشه منابع **جدید**
با **اسم‌های دلخواه** می‌سازد: ازت می‌خواهد یک اسم برای ورکر انتخاب
کنی (یا خودش یک اسم رندوم می‌گیرد)، و در اولین نصب روی یک اکانت،
برای ساب‌دامین workers.dev هم همین‌طور. این اسم‌ها دو بخش آدرس ثابتت
هستند، پس باید مال خودت باشند، نه یک پیش‌فرض مشترک — اگر همه کاربران
ریپو یک آدرس (یا یک الگوی اسم) مشترک داشتند، با یک قانون فیلتر همه‌شان
با هم بسته می‌شدند. نصب دوباره همان سرور اسم‌های ذخیره‌شده خودش را
نگه می‌دارد و دوباره نمی‌پرسد.

برای اینکه خودت اسم‌ها را انتخاب کنی:

```bash
WORKER_NAME=my-panel KV_TITLE=my-panel WORKERS_SUBDOMAIN=myname42 sudo -E bash install.sh install
```

اگر اسم ورکری که خواستی گرفته شده باشد، نصب‌کننده می‌گوید و یا اسم
آزاد بعدی را پیشنهاد می‌دهد (وقتی ترمینال است، اینتر را بزن تا همان
را بگیرد) یا خودش انتخابش می‌کند (وقتی ورودی ترمینال نیست) — مگر اینکه
آن اسم مال ورکر **همین** سرور باشد، که در این صورت همان را برمی‌دارد،
نه اینکه عوضش کند.

### کد سرور — هویت هر سرور روی کلادفلر

هر سرور یک کد کوتاه یکتا دارد: ۸ حرف اول UUID هویتش (`SERVER_CODE`
در state.env، که `show` و بلوک SAVE هم نشانش می‌دهند — مثلاً
`5c0b21ef`). این کد همراه `server:id` در namespace مربوط به KV مهر
می‌شود، پس **همه‌چیز روی کلادفلر برای آن سرور به همان کد وصل است** —
ورکرش، KVاش، لینک‌های سابکریپشنش. اجرای دوباره `install` یا
`deploy-worker` روی همان سرور اسم‌ها و namespace ذخیره‌شده خودش را
دوباره استفاده می‌کند و هیچ‌وقت چیز جدید نمی‌سازد.

اگر `state.env` زمانی گم شود (حذف شده باشد، یا دیتابیس بدون آن
برگردانده شده باشد)، نصب‌کننده از صفر شروع نمی‌کند: قبل از ساختن چیز
جدید، KVهای اکانت را می‌گردد و دنبال namespaceای می‌گردد که `server:id`
(یا `server:code`) آن با UUID یک کلاینت در دیتابیس همین پنل بخورد، و
همان ورکر + KV را برمی‌دارد — اسم ورکر، namespace، UUID کلاینت و سکرت
سابکریپشن را از دیتابیس پنل برمی‌گرداند — پس آدرس ثابت همان می‌ماند.

ساب‌دامین workers.dev مال **اکانت** کلادفلر است، نه یک سرور — همه
ورکرهای آن اکانت در آن شریک‌اند، و آدرس ثابت همیشه
`<worker-name>.<subdomain>.workers.dev` است (آدرس تک‌بخشی
`<name>.workers.dev` وجود ندارد). در نصب تازه، اگر اکانت از قبل
ساب‌دامین داشته باشد نصب‌کننده اول می‌پرسد — نگهش دارم یا عوضش کنم —
به‌جای اینکه بی‌صدا اسم قدیمی را نگه دارد. روی سروری که از قبل نصب
شده، برای عوض کردنش بزن:

```bash
sudo sui-vpn change-subdomain myname42
```

این آدرس همه ورکرهای آن اکانت را با هم عوض می‌کند، پس بعدش روی هر
سرور دیگر `sudo sui-vpn deploy-worker` را دوباره بزن تا آدرس ورکر
ذخیره‌شده‌اش تازه شود (و لینک‌های سابکریپشن جدید را از پنل هر سرور
بده).

اگر دو سرور یک ورکر + KV را شریک شوند، روی هم `panel:host` (آدرس ثابت
پنل بین دو پنل جابه‌جا می‌شود)، `panel:subjson`، متغیر `SUB_SECRET` و
کلیدهای اسم کاربر مشترک را بازنویسی می‌کنند — نشانه کلاسیکش این است که
پنل «بالا نمی‌آید» ولی کانفیگ‌های VPN کار می‌کنند. نصب‌کننده نمی‌گذارد
این اتفاق بیفتد: `sync.py` هر namespace را با `server:id` مهر می‌زند و
`deploy-worker` **متوقف می‌شود** اگر namespace مال سرور دیگری باشد
(کد آن سرور دیگر و دستور دادن اسم‌های جدا به این سرور را چاپ می‌کند).

اگر اشتباهی یکی را شریک کردی؟ روی سرور دوم نصب را دوباره اجرا کن —
برخورد را تشخیص می‌دهد، یک ورکر + KV جدا می‌سازد، کلاینت‌های آن سرور
را آنجا دوباره سینک می‌کند و لینک‌های پنلش را به آدرس جدید وصل می‌کند.
بعد آدرس ثابت پنل سرور اول را درست کن: سینک آن فقط وقتی چیزی عوض شده
باشد می‌نویسد، پس `panel:host` کهنه‌ای که سرور دیگر گذاشته می‌ماند تا
به‌زور بازنویسی شود:

```bash
sudo sui-vpn sync-now --force
```

(و اگر سروری اصلاً آدرس ثابت نگرفت، `show` می‌گوید "worker not
deployed yet" — دوباره `deploy-worker` را بزن و خط "worker URL" را
ببین؛ اگر توکن، اکانت یا قدم KV خراب باشد بلند خطا می‌دهد.)

## تنظیمات routing پنل — هر تنظیمی روی کل کانفیگ اعمال می‌شود

هر قانون routing که در پنل بگذاری به کلاینت‌ها می‌رسد: سینک هر سه
جایی را که s-ui تنظیمات routing را نگه می‌دارد می‌خواند — Subscription
JSON Extension (`subJsonExt`، رابط پیشرفته / صفحه Rules)، قالب JSON
سابکریپشن (`subJson`)، و route/dns کانفیگ اصلی (`config`) — آن‌ها را
با هم ترکیب می‌کند و به‌صورت `panel:subjson` به ورکر می‌فرستد.
تنظیمات تک‌مقداری (DNS، `final`، `default_domain_resolver`) از
بالاترین منبعی که آن را تنظیم کرده باشد می‌آیند؛ `rules` و `rule_set`
از هر سه منبع با هم ترکیب می‌شوند، پس قانونی که در هر جایی بگذاری
اعمال می‌شود. قانون بعد از سینک بعدی (حداکثر ۶۰ ثانیه) و بعد از Update
سابکریپشن در اپ کلاینت، اثر می‌کند.

مثال — این‌ها را در Subscription JSON Extension پنل بگذار:

```json
{
  "rules": [
    { "domain_suffix": ["doubleclick.net", "googlesyndication.com"], "outbound": "block" },
    { "domain_suffix": [".cn"], "outbound": "direct" }
  ]
}
```

اولی تبلیغات را برای همه کلاینت‌ها مسدود می‌کند؛ دومی سایت‌های چینی را
مستقیم می‌فرستد. همین برای سایت‌ها و اپ‌های ایرانی هم کار می‌کند — و
ورکر بای‌پس داخلی خودش را (`site-ir`: همه دامنه‌های `.ir` به‌علاوه
سرویس‌های بزرگ ایرانی روی `.com` و `.org`، و `geoip-ir` برای IPهای
ایرانی) **اول** نگه می‌دارد، پس قانون آماده قالب پنل که ایران را به
proxy می‌فرستد، هیچ‌وقت نمی‌تواند بی‌صدا آن را خنثی کند. یک استثنا:
قانون صریحی که *خودت* در پنل بنویسی و ایران را به `proxy` بفرستد اثر
نمی‌کند — بای‌پس همیشه اول ارزیابی می‌شود. این عمدی است، نه باگ.

دو محافظ هم هست: قانونی که outboundای را نام ببرد که در پروفایل وجود
ندارد (یک تگ سمت سرور از کانفیگ اصلی، یا یک تایپو) به‌جای اینکه پروفایل
را برای همه کلاینت‌ها خراب کند، توسط ورکر کنار گذاشته می‌شود؛ و قانونی
که به rule-setای اشاره کند که هیچ‌جا تعریف نشده، همین‌طور کنار گذاشته
می‌شود.

این لیست مخصوص ایران است. برای کشور دیگر، لیست `domain_suffix` را در
`worker.js` (rule-set به‌نام `site-ir`) و آدرس `geoip-ir` را عوض کن و
بعد `install.sh deploy-worker` بزن.

**Hiddify / v2rayNG فقط یک لینک vless به صورت base64 می‌گیرند که
اصلاً routing ندارد — هیچ تنظیم پنلی به آن‌ها نمی‌رسد.** برای این اپ‌ها
جداسازی را داخل خود اپ تنظیم کن (Hiddify → Settings → Routing /
GeoIP rules). فقط پروفایل JSON سینگ‌باکس (اپ رسمی sing-box) تنظیمات
routing پنل را حمل می‌کند.

## نسخه‌های پشتیبانی‌شده

- **s-ui:** نصب‌کننده به‌صورت پیش‌فرض جدیدترین نسخه گیت‌هاب را
  می‌گیرد؛ با `SUI_VERSION=1.6.8` یک نسخه را ثابت کن (نسخه‌ای که این
  ریپو اول با آن ساخته شد).
- **cloudflared:** ثابت روی 2026.11.2 با چک sha256.
- **هسته sing-box:** همان چیزی که s-ui نصب‌شده همراه خودش دارد (پروفایل
  ورکر برای فرمت JSON فعلی sing-box ساخته شده).
- **پلن رایگان کلادفلر:** ۱۰۰ هزار درخواست ورکر در روز، ۱۰۰ هزار
  خواندن KV در روز، ۱۰۰۰ نوشتن KV در روز — پایین‌تر در محدودیت‌های
  شناخته‌شده ببین.

## محدودیت‌های شناخته‌شده

- **تونل موقت SLA ندارد.** کلادفلر می‌تواند تونل `trycloudflare.com` را
  محدود یا قطع کند و آدرس آن با هر ری‌استارت عوض می‌شود (ورکر این را از
  کلاینت پنهان می‌کند). اگر آدرس پایدار می‌خواهی، تونل موقت را با **تونل
  نام‌دار + یک دامنه ارزان جدا** جایگزین کن — طراحی ورکر و سابکریپشن
  همان می‌ماند.
- **Hysteria2 از تونل کلادفلر رد نمی‌شود** (UDP/QUIC از آن عبور
  نمی‌کند). فقط مستقیم به IP سرور کار می‌کند، یعنی فقط روی شبکه‌هایی که
  آن IP را فیلتر نمی‌کنند، و به پورت UDP عمومی و گواهی TLS نیاز دارد.
  مسیر همه‌اپراتوری همین VLESS+WS است.
- **IP خروجی همان IP سرور است.** تونل IP سرور را از شبکه‌هایی که آن را
  فیلتر می‌کنند پنهان می‌کند؛ ترافیک هنوز از همان IP خارج می‌شود.
- پلن رایگان کلادفلر: ۱۰۰ هزار درخواست ورکر در روز، ۱۰۰ هزار خواندن KV
  در روز، ۱۰۰۰ نوشتن KV در روز. فقط درخواست‌هایی که واقعاً به ورکر
  می‌خورند جزو آن ۱۰۰ هزار تا حساب می‌شوند — آپدیت سابکریپشن و باز کردن
  صفحه‌های پنل، که روزی چند صد تا بیشتر نمی‌شود. **ترافیک دیتای VPN که
  از تونل موقت می‌گذرد اصلاً درخواست ورکر نیست و هیچ‌وقت حساب
  نمی‌شود**: مسیرش گوشی ← لبه کلادفلر ← `cloudflared` است و هیچ‌وقت به
  ورکر نمی‌رسد. سینک هم فقط وقتی چیزی واقعاً عوض شده باشد در KV
  می‌نویسد.
